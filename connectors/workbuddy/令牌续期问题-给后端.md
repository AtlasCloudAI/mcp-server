# WorkBuddy 连上 Atlas 后隔一会儿就要重新授权

**结论先说：原因查清了，修法在我们这侧，不需要你们做任何事。** 这份是同步进展，不是提需求。

下面每一环都写了判据，可以自己复核，不必信我的转述。

## 现象

WorkBuddy 连上 dev 的 Atlas MCP，授权成功、12 个工具可用。过一会儿再用就变成未授权，要重新走一遍浏览器授权。客户端日志里是反复的 `Unauthorized`，跨了 21 小时仍在出现。

## 为什么会这样

**一、我们的资源元数据没有公示 `offline_access`**

```
GET https://atlascloud-mcp.dev.atlascloud.ai/.well-known/oauth-protected-resource
  scopes_supported: ["tasks:read", "tasks:write", "billing:read"]
```

**二、客户端就按这个清单去申请授权**

WorkBuddy 内置官方 MCP TypeScript SDK 1.24.3。它组授权 URL 时的取值是
`401 头里的 scope || 资源元数据的 scopes_supported || 客户端自己的 clientMetadata.scope`。
前两项都由我们给，所以它请求的范围里没有 `offline_access`，它也不会自己补。

**三、授权范围里没有 `offline_access` 就不签发 refresh token**

```go
// console/backend/pkg/authzserver/provider.go:67
RefreshTokenScopes: []string{ScopeOfflineAccess},
```

**四、客户端拿不到 refresh token，就只能整个重新授权**

SDK 的逻辑是：本地没有 refresh token 就作废已注册的客户端、重新注册、重新走浏览器授权。
而 access token 有效期 15 分钟（`config/authorization_server.go:15` 的默认值，dev 的
`config.toml` 没有覆盖），所以每过期一次就打断一次。

到这里就能回答群里那个问题了：**是 access token，也确实该靠 refresh 换 —— 但我们这条链上
从来没产生过 refresh token，SDK 没有东西可换。**

## 两个已经验证过的前提

**动态注册出来的客户端本来就允许申请 `offline_access`。** 实测一次 DCR 注册，响应里的允许集是：

```
scope: "openid offline_access tasks:read tasks:write billing:read"
grant_types: ["authorization_code", "refresh_token"]
```

所以这不是权限没开，是**我们没说要，对方就没给**。这也是为什么修法在我们这侧。

**Codex 那条路不会被影响。** 我担心过公示之后 Codex（走 CIMD，客户端来源和 DCR 不同）
会撞 `invalid_scope`，查下来两条路最终走到同一个函数，允许集起手就带这两个协议范围：

```go
// registry.go:98
func (r *resourceRegistry) scopesForResources(identifiers []string) []string {
	out := []string{ScopeOpenID, ScopeOfflineAccess}
	...
```

## 我们要做的

在资源元数据和 401 挑战头里公示 `offline_access`，让客户端的授权请求带上它。改动全在
`mcp-server` 仓，不涉及 kubedl。

用户侧的变化是同意页会多一项「在你不在场时继续访问」——你们的同意页已经有这一项的说明文案
（`consent_page.go` 的 `consentOfflineAccessNotice`），不用新做。

改完的效果：**授权一次之后不用再管。** access token 照样 15 分钟过期，但客户端会静默续期，
用户无感。真正需要再授权的只有三种情况：连续 90 天没用过（refresh token 有效期，而且你们
实现了滚动轮换，每次续期都重置）、用户主动撤销、重装客户端。

**验证判据**：授权成功 → 等 15 分钟以上 → 回 WorkBuddy 调一个工具。不弹浏览器就是成了。
我们在 dev 上验完把结果同步给你们。

## 你们不用做任何事

顺带说明两件想过但决定不做的，免得你们再花时间：

**没打算让你们改 `RefreshTokenScopes`。** 抽查了几家同样上架 WorkBuddy 的第三方，Canva、
分贝通的资源元数据同样不公示 `offline_access` 却不掉线，说明它们的授权服务器没把 refresh
token 绑在这个范围上。但 `registry.go` 里那段注释写得很清楚，这里是刻意把 `offline_access`
当成「要用户单独点头的长期离线访问」，还专门处理了「客户端用不上却进了授权记录」的隐患。
我们这侧改公示就能解决，没必要动这个语义。

**access token 的 15 分钟也不用改。** 修好续期之后 15 分钟和 60 分钟对用户完全一样，都是
静默续期。提到 1 小时只能少四倍的续期请求和令牌表轮换写入，属于保养不是修复，你们看排期，
不做也不影响上面那条生效。
