# WorkBuddy 连上 Atlas 后隔一会儿就要重新授权

先说结论：**主要修法在我们这侧，不用你们动手。** 但有一条配置建议顺手改一下，另有一条方案要是你们反对前一条才用得上。

下面的因果链每一环都写了判据，可以逐条自己复核，不必信我的转述。

## 现象

WorkBuddy 连上 dev 的 Atlas MCP，授权成功、12 个工具可用。过一会儿再用就变成未授权，要重新走一遍浏览器授权。连续干活大约每 15 分钟被打断一次；隔一阵子回来用，基本每次都要重连。

客户端日志里是反复的 `Unauthorized`（2026-09-20 12:33 起，跨了 21 小时仍在出现）。

## 因果链

**一、我们的资源元数据没有公示 `offline_access`**

```
GET https://atlascloud-mcp.dev.atlascloud.ai/.well-known/oauth-protected-resource
  scopes_supported: ["tasks:read", "tasks:write", "billing:read"]
```

**二、客户端就按这个清单去申请授权**

WorkBuddy 内置官方 MCP TypeScript SDK 1.24.3，它组授权 URL 时的取值是
`401 头里的 scope || 资源元数据的 scopes_supported || 客户端自己的 clientMetadata.scope`。
前两项都由我们给，所以它请求的范围里没有 `offline_access`，它也不会自己补。

**三、授权范围里没有 `offline_access` 就不签发 refresh token**

```go
// console/backend/pkg/authzserver/provider.go:67
RefreshTokenScopes: []string{ScopeOfflineAccess},
```

**四、客户端拿不到 refresh token，就只能整个重新授权**

SDK 的逻辑是：发现本地没有 refresh token 就作废已注册的客户端、重新注册、重新走浏览器授权。
而 access token 的有效期是 15 分钟：

```
console/backend/pkg/config/authorization_server.go:15
DefaultAuthServerAccessTokenTTLMinutes = 15
```

dev 的 `config.toml` 没有覆盖这一项，用的就是默认值。

## 一个已经验证过的前提

动态注册出来的客户端**本来就允许申请 `offline_access`**。实测一次 DCR 注册，响应里的允许集是：

```
scope: "openid offline_access tasks:read tasks:write billing:read"
grant_types: ["authorization_code", "refresh_token"]
```

所以这不是权限没开的问题，是**我们没说要，对方就没给**。这也是为什么主要修法在我们这侧。

## 三个方案

### 方案一 · 我们在资源元数据里公示 `offline_access`（推荐，我方改）

改我们 MCP 服务的公示清单，让客户端的授权请求带上它。

- **谁做**：我们。改 `mcp-server` 的 `ADVERTISED_SCOPES` 与一条测试断言，不涉及 kubedl。
- **代价**：契约 v3 §8 原话是「refresh token 是客户端与 AS 之间的事，不进资源的 scope 清单」。
  这句话的前提是客户端会自己申请 —— 实测这个 SDK 不会。要和契约方说一声这条前提不成立。
- **用户侧变化**：同意页会多一项「在你不在场时继续访问」。你们的同意页已经有这项的说明文案
  （`consent_page.go` 的 `consentOfflineAccessNotice`），不用新做。
- **判据**：授权后等 15 分钟以上再调一次工具，不弹浏览器就是成了。

### 方案二 · access token 有效期从 15 分钟提到 60 分钟（建议顺手改，你们改）

- **谁做**：运维。`atlascloud-dev` 的 `config` ConfigMap 里 `config.toml` 的
  `[authorization_server]` 段加 `access_token_ttl_minutes = 60`，重启 backend。**不用发版。**
- **注意**：这条**单独做解决不了问题**，只是把打断从每 15 分钟变成每 60 分钟。
  它的价值是配合方案一 —— 修好续期之后，静默续期的次数直接降到四分之一。
- **依据**：WorkBuddy 开放平台文档对接入方的建议是 access token 约 1 小时、
  refresh token 不少于 30 天。你们的 refresh token 默认 90 天，那一项是够的。

### 方案三 · `RefreshTokenScopes` 留空，授权码一律签发 refresh token（不推荐）

- **谁做**：你们，改 `provider.go:67`。
- **为什么会想到它**：抽查了几家同样上架 WorkBuddy 的第三方，Canva、分贝通的资源元数据
  同样不公示 `offline_access`，但它们不掉线 —— 说明它们的授权服务器没把 refresh token
  绑在这个范围上。
- **为什么不推荐**：`registry.go` 里那段注释写得很清楚，`offline_access` 被刻意当成
  「要用户点头才给的长期离线访问」，还专门处理了「客户端用不上却进了授权记录」的隐患。
  留空等于把这个语义去掉，用户不再对长期访问单独点头。
- **只有在契约方明确反对方案一时才考虑这条。**

## 建议

**方案一 + 方案二。** 方案一是根治且不用你们动手，方案二是一行配置、顺手把频率再降四倍。

我们这侧会做的：改公示清单、改测试、发 dev 镜像，然后用「授权后等 15 分钟再调工具，看弹不弹浏览器」验一次，结果回给你们。

需要你们的只有方案二那一行 ConfigMap 配置。

## 两件不用做的

- **不用改动态注册。** DCR 已经在 dev 跑通，客户端允许集里本来就有 `offline_access`。
- **不用动网关。** 这次不涉及新的根路由，CF Access 的放行清单不需要变。
