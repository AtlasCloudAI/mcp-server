## 这个服务是干什么的

用户在 Codex 里装一个插件，就能直接生成图 / 视频 / 音频，费用记在他自己的
Atlas 账户上 —— **不需要贴 API key**。插件连到我们这个 MCP 服务，服务把用户
自己的 OAuth 令牌换成一枚面向模型 API 的令牌再去调用。

调用方向（看一眼能省很多沟通）：

```
用户的 Codex
     │
     │  只连这一个域名（下面的它一个都不碰）
     ▼
mcp.atlascloud.ai  ──►  MCP Pod  ──┬──►  auth.atlascloud.ai    换令牌 / 取 JWKS 验签
                                   ├──►  api.atlascloud.ai     余额 · 报价 · 生成 · 轮询
                                   ├──►  *.aliyuncs.com        取产出图，转成对话里能看的图
                                   └──►  Redis                 幂等键（防重复提交）
```

### 端口

| 层 | 端口 | 出处 |
|---|---|---|
| Cloudflare 回源 | 443 | HTTPS 打到集群网关 |
| Service | 80 | `atlascloud-openai-mcp`，`targetPort: http` |
| **容器** | **3000** | env `PORT=3000`，containerPort 名叫 `http` |

Dockerfile 写的是 `EXPOSE 3000 3001`，但**只需要 3000**。3001 是自建授权页的
端口（同一个镜像里的另一个程序，入口 `dist/auth.js`），官网 OIDC 上线后已停用，
生产不部署。清单里也只接了 3000。

## 项目架构依赖

### 进程与入口

同一个镜像里有两个入口，用的是同一套工具实现：

| 入口 | 传输 | 用在哪 | 生产部署 |
|---|---|---|---|
| `dist/http.js` | Streamable HTTP + OAuth 2.1 | Codex / ChatGPT 远端连接 | **就是这个**（Dockerfile 的 `CMD`） |
| `dist/index.js` | stdio | 用户本机装 MCP、自己贴 key | 不部署 |
| `dist/auth.js` | HTTP :3001 | 自建授权服务器 | **不部署**，被官网 OIDC 取代 |

两个入口都走 `src/server.ts` 注册工具，所以工具行为一致；差别只在传输层和凭据来源。

### 内部分层

```
入口   http.ts / index.ts
         │
服务器  server.ts          注册全部工具，按 profile 决定装哪几个
         │
工具层  src/tools/         9 个文件：image · video · audio · llm · models
         │                 docs · upload · account · quick-generate
服务层  src/services/      14 个文件：api-client（含 SSRF 闸门 + 代理）
         │                 token-exchange · credential-resolver · idempotency
         │                 generation · spend-policy · media-preview
         │                 generation-confirmation · request-context
工具函数 src/utils/        4 个文件：formatter · prompt-gen · schema-validator
         │                 error-handler
配置     src/config.ts     zod schema，启动即校验，贯穿所有层
```

| 包 | 用途 | 生产是否需要 |

### 外部服务依赖

| 依赖 | 失效后果 | 降级方式 |
|---|---|---|
| `auth.atlascloud.ai` | **Pod 不就绪**，或全部请求 401 | 无。fail-closed |
| `api.atlascloud.ai`（backend） | 查不到余额和模型 | 无 |
| `api.atlascloud.ai`（aiproxy） | 报价和生成全失败 | 无 |
| Redis | 启动失败 | 无。production 强制 |

在计费和鉴权路径上，静默降级比直接失败危险得多。

## 运维要做的六步

按顺序，有先后依赖。

### 1. 配 `mcp.atlascloud.ai` 的回源

现在这个 host 三条路径全返回 `525`，而且响应头里一个源站指纹都没有
（`server: cloudflare`，没有 `x-envoy-*`），说明请求根本没到源站，
CF 和源站的 TLS 握手就失败了。回源指到部署 MCP 的那个集群网关即可。

同时把这个 host 的超时给到 **120 秒**、请求体上限 **256k**。MCP 是流式长连接，
默认 60 秒会把正在生成的请求掐断 —— 表现是用户那边生成到一半突然断开，很难查。

> **做完告诉我们：** 回源已指向哪个网关

### 2. 确认这个 host 没有继承 Cloudflare Access 策略

实测下来，生产环境这几个机器调用的 host 本来就**不在** Access 后面：

| host | 状态 | 在 Access 后面吗 |
|---|---|---|
| `api.atlascloud.ai` | 200 | 不在 |
| `auth.atlascloud.ai` | 200 | 不在 |
| `api.dev.atlascloud.ai` | 302 → `cloudflareaccess.com/cdn-cgi/access/login` | 在 |
| `console.dev.atlascloud.ai` | 302 → 同上 | 在 |

**Access 在这个账号里是 dev 环境的东西。** 所以这一步大概什么都不用做，
确认 `mcp.atlascloud.ai` 和 `api.atlascloud.ai` 配得一样就行。

如果它确实继承到了 Access 策略，需要设成 **Bypass**（不是 Allow）：
这个域名是给程序调的，调用方没有浏览器会话，Allow 策略照样会把它 302
到登录页，插件就连不上了。

验证别用自己平时的浏览器 —— 你身上带着 `CF_Authorization` 这个 cookie，
看起来一定是通的。**用无痕窗口**打开 well-known，直接看到 JSON 才算过。

如果公司规定不允许对这个 host 放行 Access，还有一条退路：把这条 DNS 记录从
Proxied 改成 **DNS only（灰云）**。Access 只作用于 proxied 主机，灰云之后
Access 整个不介入，**525 也一起没了**（没有 CF→源站这一跳）。代价是源站 IP
暴露、前面没有 CF 的 WAF/DDoS。证书没问题：集群里 `letsencrypt-dns01` issuer
是 Ready 的，dns01 走 TXT 记录，与代理开关无关。

> **做完告诉我们：** 无痕窗口能直接见 JSON

### 3. 确定部署位置

两种都行，差别只在合规口径。

**留在现集群的 `mcp-servers` 命名空间最省事**：镜像拉取凭据
`atlas-registry-secret`、cert-manager 的 `letsencrypt-dns01` issuer 都是现成的，
而且这个命名空间本来就在对外服务 `agents-playground.atlascloud.ai` 这个生产域名，
有先例。

换到生产集群的理由是「生产流量不跑在 dev 节点上」，以及上游可以走内网。
换的话请顺带说明生产网关是 higress 还是 nginx-ingress —— ingress 注解写法不一样。

> **做完告诉我们：** 集群 + 命名空间 + 网关类型；换集群的话还要一个能操作的入口

### 4. 出网放行四个目标

这些全是 **MCP Pod 自己发起**的出站请求，调用方一个都不碰。

| 目标 | 用途 |
|---|---|
| `auth.atlascloud.ai` | 取授权服务器元数据、拉 JWKS 验签、做令牌交换。**不通则 Pod 永不就绪** |
| `api.atlascloud.ai` | 余额、报价、提交生成、轮询结果。若给了内网地址则换成内网 |
| `static.atlascloud.ai` | 拉模型 schema 与文档 |
| `*.aliyuncs.com` | 取产出图片转成对话里可见的图。不通只影响预览，不影响生成 |

第一条最要紧：拉不到 `auth.atlascloud.ai`，启动自检过不去，Pod 会永远停在
未就绪，而且日志里看不出是网络问题。

> **做完告诉我们：** 放行完成；另外如果生产 backend 和 aiproxy 有集群内
> Service DNS，一并给我们，可以省一跳公网

### 5. 建两个 Secret

清单里不含任何 Secret，需要先手工建好再 apply。一共两个、四个键：

| Secret | 键 | 值 |
|---|---|---|
| `atlascloud-openai-plugin` | `redis-url` | `redis://:密码@主机:6379`。**必须带密码**，无密码启动会直接报错 |
| | `generation-confirmation-secret` | 我们给（32 字节随机） |
| | `openai-challenge-token` | 我们给 |
| `atlas-mcp-token-exchange` | `client-secret` | 由授权服务器管理员登记客户端时产生，见下一节 |

清单里自带一套单副本 Redis（StatefulSet + Service + NetworkPolicy），不用额外准备。
**里面只有幂等键，没有任何用户凭据**（换来的令牌只在进程内存，不落盘），
所以不需要专用实例 —— 想用托管或现成的 Redis，把 `redis-url` 换掉即可。

> **做完告诉我们：** 两个 Secret 已建

### 6. 填三个占位符，然后 apply

清单在 `deploy/kubernetes/production.example/`。镜像已经填好，剩下三个地方
都写成了显眼的 `REPLACE_WITH_*`：

| 占位符 | 填什么 | 谁给 |
|---|---|---|
| `REPLACE_WITH_PRODUCTION_CLIENT_ID` | token-exchange 客户端 ID | AS 管理员 |
| `REPLACE_WITH_BACKEND_BASE_URL` | 生产 backend 内网地址，拿不到就填 `https://api.atlascloud.ai` | 运维 |
| `REPLACE_WITH_AIPROXY_BASE_URL` | 生产 aiproxy 内网地址，同上 | 运维 |

先渲染出来看一眼，再 dry-run，最后才真 apply：

```bash
# 1. 看渲染结果（不连集群）
kubectl kustomize deploy/kubernetes/production.example

# 2. 服务端校验，不落盘
kubectl apply --server-side --dry-run=server -k deploy/kubernetes/production.example

# 3. 真的部署
kubectl apply -k deploy/kubernetes/production.example
kubectl -n mcp-servers rollout status statefulset/atlascloud-plugin-redis
kubectl -n mcp-servers rollout status deployment/atlascloud-openai-mcp
```

清单里的镜像是**按 digest 固定**的，不是按标签 —— 标签能被后来的推送覆盖，
digest 不能。dev 和生产之前共用 `20260910-preview-logs` 这一个标签，就是这么
出的问题。

```
registry.atlascloud.ai/vcv-dg/atlascloud-mcp-openai-plugin
  :v2.1.0
  @sha256:79470348a1ecd8dda2cdf1f568b665c30f059fc7f2301c28ec10218cac3439da
```

> **做完告诉我们：** `rollout status` 的输出；起不来就把
> `kubectl -n mcp-servers logs deploy/atlascloud-openai-mcp` 前 50 行发我们

## 怎么算部署成功

三条，全过才算：

```bash
# 1. Pod 就绪（就绪即代表启动自检已经和授权服务器对账通过）
kubectl -n mcp-servers rollout status deployment/atlascloud-openai-mcp

# 2. 公网能拿到资源元数据，且返回体里的域名是生产的
curl -sS https://mcp.atlascloud.ai/.well-known/oauth-protected-resource
#    期望：{"resource":"https://mcp.atlascloud.ai/mcp",
#           "authorization_servers":["https://auth.atlascloud.ai"], ...}

# 3. 无痕窗口打开同一条 URL，直接见 JSON
#    （证明没有被 Access 拦，或 Access 是 Bypass 而不是 Allow）
```

三条都过之后我们会用 Codex 真连一次、跑一次最便宜的生成，确认账单记在

## 出问题先查这张表

这些都是我们在 dev 上真踩过的，症状和原因一一对应。

| 看到什么 | 几乎一定是 |
|---|---|
| `525` | 第 1 步没做，或源站那边没有这个 Host 的证书。**响应头里有没有 `x-envoy-*` 能一眼分清**：没有就是没到源站，有就是源站自己的问题 |
| `302` 到登录页 | Access 设成了 Allow 而不是 Bypass。浏览器里测不出来，必须无痕 |
| `404` | 请求到了源站但 ingress 的 host 没匹配上。检查是不是同一个 host 被两条 ingress 抢了 —— dev 上就有一条从网关控制台建的路由撞了同一个域名 |
| Pod 一直不就绪 | 多半是 `auth.atlascloud.ai` 出网不通（第 4 步），其次是 JWKS 地址写错。它是 fail-closed 设计：对不上就不放行，宁可不就绪也不签发错误的令牌 |
| `ImagePullBackOff` | 命名空间里没有 `atlas-registry-secret`，或生产集群访问不到 `registry.atlascloud.ai` |
| 每个请求都 `401` | `MCP_OAUTH_AUDIENCE` 和授权服务器里登记的资源标识不一致。差一个斜杠也不行 |
| 生成到一半断开 | 网关超时没给到 120 秒（第 1 步） |
| 图片不显示但生成成功 | `*.aliyuncs.com` 没放行。这条是 fail-open 的，只掉预览不影响出片，日志里搜 `[media-preview]` 能看到原因 |

排障主要靠两类日志行：`[generation]`（提交与产出）和 `[media-preview]`（图片预览）。
请确认运维侧能捞到 Pod 日志，这比任何监控面板都直接。

## 关于把分支直接给运维

仓库是公开的，分支可以直接给。但请**不要从分支自己构建镜像** —— 这个分支
还没合进 `main`，镜像由我们用流水线统一构建并给出 digest，这样线上跑的是哪份
代码才能追溯。

清单目录名带 `.example` 后缀是有意的：它含三个占位符，直接 apply 会失败。
填完就是正式清单，不需要改名。
